# S3 Store

`S3Stores` implements [Stores]/[Store] on top of any S3-compatible object store
(AWS S3, MinIO, ...) using plain HTTP. It has **no AWS SDK dependency**: requests
are signed with AWS Signature Version 4 directly (see `sigv4.go`), which is all a
private bucket needs.

Like every `flob` backend it keeps no database — the bucket layout *is* the index —
and it preserves the two invariants of the design: content is **deduplicated**
across stores, while a blob is **visible only to the store that added it**.

## Layout

Everything lives in one bucket, optionally under a shared key `prefix`:

```
<prefix>blob/<algo>/<hex>            the one shared copy of each blob
<prefix>refs/<algo>/<hex>/<store>    a per-store reference marker (empty body)
```

- `blob/<algo>/<hex>` is content-addressed: identical content resolves to the same
  key regardless of which store adds it, so it is stored **once**. This is the
  dedup mechanism — the S3 equivalent of the OS backend's shared inode.
- `refs/<algo>/<hex>/<store>` is a tiny marker object whose existence means "this
  store references this digest". Its `x-amz-meta-*` metadata carries the store's
  labels and the blob size; the object body is empty.

`<algo>` is `sha256` and `<hex>` is the 64-character lowercase digest.

## Visibility & deduplication

The single rule that makes both properties hold:

> Every **existence** decision reads the per-store `refs/` marker; the shared
> `blob/` object is consulted only to move bytes (upload / download / reclaim) and
> its presence is **never** surfaced to the caller.

Consequently:

- `Get`, `Open`, `Label`, and `Add`'s duplicate check all `HEAD refs/.../<store>`.
  A store that never added a digest gets `ErrNotExist`, even though the shared
  `blob/` object exists for another store. Store A's blob is invisible to store B.
- `Add` writes `blob/...` only if it is missing (a `HEAD` first avoids re-uploading
  content another store already put there), then writes the store's `refs/` marker.
  The big bytes are shared; each extra store costs one empty marker object.

This is API-level isolation. The shared `blob/` object is still a single physical
copy, so it is not isolated at the storage layer (anyone with bucket-level read
access sees the pooled content, and an upload-skip is observable as a timing
difference). If you need storage-layer isolation, do not share content across
stores — that trade-off is inherent to cross-store dedup.

## Operation mapping

| `Store` method | S3 requests |
| --- | --- |
| `Add`    | `HEAD refs/.../<store>` (dup) → `HEAD blob/...` → `PUT blob/...` if missing → `PUT refs/.../<store>` |
| `Get`    | `HEAD refs/.../<store>` |
| `Open`   | `HEAD refs/.../<store>` (gate + meta) → `GET blob/...` |
| `Label`  | `HEAD refs/.../<store>` → `PUT refs/.../<store>` (overwrites metadata) |
| `Erase`  | `DELETE refs/.../<store>` (the shared blob is left for out-of-band GC) |

`Add` buffers the reader to a temporary file while hashing, so the digest is known
before upload. The blob's SHA-256 *is* its digest, so it is reused verbatim as the
`x-amz-content-sha256` payload hash — no second pass over the bytes. `Open`
downloads the blob into memory to satisfy `io.ReadSeekCloser`, matching the HTTP
store.

## Labels as object metadata

Labels are stored as user metadata on the reference marker, not as a separate
object. Each label `Key: value` becomes an `x-amz-meta-Key: value` header on
`PUT refs/.../<store>`, and is read back from `HEAD`/`GET`. `Label` rewrites the
marker, replacing the whole set (the blob size is preserved in the reserved
`x-amz-meta-Flob-Size` entry).

S3 metadata constraints therefore apply to labels on this backend:

- **Reserved:** `Flob-Size` is used internally; do not use it as a label key.
- **Single value:** multi-valued labels are joined with `,` (HTTP list semantics)
  and returned as one value.
- **ASCII only** and **< 2 KiB** total for all keys and values combined (an S3
  limit). Keys are matched case-insensitively: S3 lowercases the stored key and the
  client re-canonicalizes it on read, so a canonically-formed header key (e.g.
  `Media-Type`) round-trips unchanged, while the exact casing of a non-canonical key
  is not preserved.

The filesystem and in-memory stores have no such restrictions.

## Configuration

Selected by an `s3/<name>` key under `stores`:

```yaml
stores:
  s3/main:
    # endpoint: https://s3.us-east-1.amazonaws.com  # omit to derive from region
    region: us-east-1
    bucket: my-blobs
    prefix: flob            # optional; lets several deployments share one bucket
    path_style: false       # true for MinIO and most S3-compatible servers
    access_key_id: ...
    secret_access_key: ...
    # session_token: ...    # only for temporary (STS) credentials
```

| Field | Meaning | Fallback |
| --- | --- | --- |
| `endpoint` | Service URL; empty derives `s3.<region>.amazonaws.com` | — |
| `region` | AWS region (used for signing) | `$AWS_REGION`, else `us-east-1` |
| `bucket` | Bucket holding every store (**required**) | — |
| `prefix` | Key prefix within the bucket | — |
| `path_style` | `host/bucket/key` vs `bucket.host/key` addressing | `false` |
| `access_key_id` | Access key | `$AWS_ACCESS_KEY_ID` |
| `secret_access_key` | Secret key | `$AWS_SECRET_ACCESS_KEY` |
| `session_token` | Temporary-credential token | `$AWS_SESSION_TOKEN` |

Credentials and region fall back to the standard `AWS_*` environment variables, so
secrets can stay out of the config file. **Private buckets** work as-is: every
request is SigV4-signed with these credentials.

- **AWS S3**: leave `endpoint` empty (virtual-hosted addressing is used) or set the
  regional endpoint; keep `path_style: false`.
- **MinIO / S3-compatible**: set `endpoint` to the server URL and
  `path_style: true`.

## Consistency & garbage collection

S3 is strongly read-after-write consistent for `PUT`/`GET`/`LIST`.

`Erase` removes only the store's own reference marker; the shared blob is **not**
reclaimed inline. This is a deliberate difference from the OS backend, and the reason
matters:

- In the OS backend a per-store entry is a *hard link* that physically holds the
  bytes, so removing the shared copy can never lose data — the link keeps it alive.
- An S3 reference marker is an *empty pointer object*; the bytes live in exactly one
  object, `blob/<algo>/<hex>`.

S3 offers no atomic "delete this object only if nothing else references it", so an
inline `LIST`-then-`DELETE` would be a check-then-act that can race a concurrent
`Add`: another store may have already seen the blob (and skipped its upload) but not
yet written its marker, so the `LIST` sees no references and the `DELETE` destroys
content that `Add` is about to return successfully. That is silent **data loss**, not
a reclaimable leak, so it is not done — doing it would violate the project invariant
that a committed digest always yields the right content.

Reclamation is instead deferred to an **out-of-band, grace-period sweep**, the same
choice the OS backend makes for orphan collection. Because the store never deletes a
blob, once `Add` has ensured a blob exists it stays, so a committed reference always
has readable bytes — correctness is preserved and only reclaimable space leaks (a
blob whose last reference was erased lingers until swept). Deduplication still holds:
identical content is stored once regardless of how many stores reference it. A safe
sweep deletes `blob/<algo>/<hex>` only when it has **no** `refs/<algo>/<hex>/` markers
**and** is older than the longest possible in-flight `Add`, so it cannot reclaim a
blob that a slow `Add` is still committing.
